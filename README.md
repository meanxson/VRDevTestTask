# VR-тренажёр: сценарий из групп шагов

Unity 6000.4.3f1, URP, XR Interaction Toolkit 3.4.1.

## Архитектура

Проект разделён на четыре сборки по принципам Clean Architecture, зависимости направлены строго внутрь:
`App.Presentation` и `App.Infrastructure` → `App.Application` → `App.Domain`, плюс `App.Common` без
зависимостей вовсе. **`App.Domain` и `App.Application` собраны с `noEngineReferences: true`** — их
независимость от `UnityEngine` проверяет компилятор, а не договорённость. В домене лежит вся логика
задания: неизменяемое описание сценария (`Scenario` → `StepGroup` → `Step` → `ExpectedAction`) отделено
от состояния прохождения (`ScenarioSession` → `StepGroupProgress` → `StepProgress`), поэтому повторная
попытка — это просто новая сессия на том же описании. `ScenarioSession` — единственное место, где
состояние меняется: он разбирает действие пользователя по четырём правилам (закрывает ожидание текущего
шага; повторяет уже зачтённое — игнорируем; ожидается более поздним шагом группы — нарушение порядка
и вся группа закрывается, незавершённым шагам ставится «пропущен»; всё остальное — шаг закрывается
с ошибкой) и **возвращает список произошедших доменных событий, ничего никуда не отправляя сам**.

Рассылкой занимается прикладной слой. Он состоит из юзкейсов (`StartScenarioUseCase`,
`SubmitUserActionUseCase`, `StartTrainingUseCase`, `RestartScenarioUseCase`, `ReturnToLobbyUseCase`)
и двух портов — `IScenarioSource` и `ISceneNavigator`, которые реализует инфраструктура. Всё, что
происходит по ходу сценария, уходит в собственную шину событий `App.Common.Events.EventBus` (готовые
решения запрещены заданием): она рассылает сообщение по его фактическому типу, базовым классам и
интерфейсам, а подписка возвращает `IDisposable`. Представление — это подписчики: подсветка целей,
звуковые сигналы, чек-лист текущей группы, брифинг и экран итогов. Поэтому отдельных портов на звук
и подсветку нет: они не нужны, когда зависимость строится на событиях. DI-контейнер не используется —
сборка идёт руками в `AppComposition`, а композиционный корень `AppRoot` (единственный объект,
живущий между сценами) публикует её через `AppServices` — единственное глобальное состояние в проекте,
и лежит оно в прикладном слое, чтобы представление не зависело от инфраструктуры.

## Структура

```
Assets/App/
  Code/
    Domain/          Actions, Scenarios, Execution, Events — чистый C#
    Common/          Events — собственная шина
    Application/     Ports, UseCases, Services, Composition, Messages — чистый C#
    Infrastructure/  Configuration (JSON), Navigation, Composition (AppRoot)
    Presentation/    Core, Interaction, Feedback, Ui, Bootstrap
  Config/            scenario.json — описание сценария
  Content/           Resources/AppOutline.shader — обводка
```

## Сценарий

Описание лежит в `Assets/App/Config/scenario.json` и разбирается `JsonScenarioSource`. Формат следует
образцу из задания и добавляет массив групп и необязательный список из нескольких ожидаемых действий
на один шаг:

```json
{
  "title": "Досмотр на контрольно-пропускном пункте",
  "groups": [
    {
      "title": "Проверка документов",
      "briefing": "Подойдите к стойке контроля, возьмите паспорт и подтвердите проверку.",
      "steps": [
        { "id": 1, "description": "Подойдите к стойке контроля", "expectedAction": "подойти", "target": "counter_zone" },
        { "id": 3, "description": "Встаньте к пульту и нажмите «Открыть проход»",
          "expectedActions": [
            { "action": "подойти",      "target": "control_zone" },
            { "action": "нажать кнопку", "target": "open_gate_button" }
          ] }
      ]
    }
  ]
}
```

Названия действий понимаются и по-русски (`подойти`, `граб`, `клик`, `нажать кнопку`), и по именам
элементов перечисления. Любая ошибка в файле превращается в сообщение с указанием группы и шага,
которое показывается пользователю, а не роняет сцену.

## Сборка сцены

`target` из конфигурации связывается с объектом сцены компонентом `InteractionTarget`. Рядом с ним
ставится тот компонент, который соответствует ожидаемому действию:

| Действие | Компонент | Требует |
| --- | --- | --- |
| дойти до точки | `PointOfInterestZone` | триггерный коллайдер |
| взять объект | `GrabActionReporter` | `XRGrabInteractable` |
| кликнуть лучом | `ClickActionReporter` | `XRSimpleInteractable` (плюс работает и мышь) |
| нажать кнопку UI | `UiButtonActionReporter` | `Button` |

Подсветка включается компонентом `TargetHighlighter` на том же объекте. Панели интерфейса —
`BriefingView`, `StepChecklistView`, `ResultsView`, в лобби — `LobbyMenuView`; запуск прохождения
в сцене тренировки — `TrainingSceneBootstrap`. В сцене также должен быть объект с `AppRoot`,
которому назначен файл сценария и имена сцен лобби и тренировки.

## Состояние работы

Собраны и проверены все слои: логика, шина, юзкейсы, инфраструктура и компоненты представления
компилируются, доменные правила покрыты тестами. **Сцены `Lobby` и `Training` ещё не собраны** —
их наполнение примитивами, префабами и панелями интерфейса остаётся следующим шагом.

## О наиболее гибкой системе сценариев

Ключевое решение, которое даёт гибкость, уже заложено: **описание сценария отделено от состояния
прохождения, а домен возвращает события вместо того, чтобы дёргать исполнителей**. За счёт этого
источник сценария заменяется одной реализацией `IScenarioSource` — JSON, ScriptableObject, загрузка
с сервера, — и ничего кроме неё менять не нужно.

Куда это развивать дальше:

- **Действие как расширяемая точка, а не перечисление.** Сейчас `ActionType` закрыт списком из
  задания. Следующий шаг — сделать ожидание шага условием (`IStepCondition` с методом
  `IsSatisfiedBy(UserAction)`): тогда «повернуть вентиль на 90°», «удерживать предмет 3 секунды»
  или «ответить на вопрос» добавляются новым классом условия и новым детектором в сцене, без правок
  домена и формата файла — в JSON появляется лишь новый тип условия.
- **Порядок как свойство группы, а не константа.** Линейная последовательность с закрытием группы
  при нарушении — частный случай. Стоит вынести его в стратегию (`IOrderPolicy`): линейная,
  свободная (шаги в любом порядке), частично свободная. Тогда одна и та же система обслуживает
  и строгий регламент, и свободный осмотр.
- **Ветвление и оценка.** Группа может иметь условия перехода, а не только «следующая по списку»,
  а у шага — вес для итоговой оценки. И то, и другое ложится на существующую модель: ветвление —
  это поле в описании группы, оценка — свойство шага, и оба читаются тем же источником.

Чего делать не стоит: превращать сценарий в граф с логикой внутри узлов. Как только правила переезжают
в данные, их перестают покрывать тесты, а отлаживать сценарий приходится в редакторе вместо кода.
Правила должны оставаться в домене, а в конфигурации — только то, из чего сценарий состоит.
